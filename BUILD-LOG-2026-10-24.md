# Build log — 2026-10-24

## Share-expiration reminder emails (DONE — backend, verified end-to-end)

Picked from `BUILD-LOG-2026-10-23.md`'s remaining backlog item #8. This is
also the single biggest drop-off risk named in `STRATEGY-2026-10-23.md`
section 4 step 6: because Send has no accounts requirement and (until now)
no re-engagement surface, a sender with a share about to expire had zero
warning and zero reason to come back before the link and files disappeared
for good.

- `backend/prisma/schema.prisma`: new `Share.expirationReminderSentAt
  DateTime?` column. Migration `20261023211837_add_share_expiration_reminder`
  created and applied against a temp SQLite DB — ready for `prisma migrate
  deploy` on next real deploy.
- `backend/prisma/seed/config.seed.ts`: new admin-configurable settings —
  `share.enableShareExpirationReminders` (boolean, default `true`),
  `share.expirationReminderThreshold` (timespan, default `1 days`),
  `email.shareExpirationReminderSubject` / `...Message` (editable templates,
  same pattern as the existing download-notification templates).
- `backend/src/email/email.service.ts`: `sendShareExpirationReminder()` —
  builds both the public share URL and a link straight to the share's
  analytics/management page (`/account/shares/:id/analytics`, shipped last
  round), with `{name}`, `{shareName}`, `{fileCount}`, `{expiresIn}`,
  `{shareUrl}`, `{manageUrl}` template variables.
- `backend/src/jobs/jobs.service.ts`: new `@Cron("*/15 * * * *")
  sendShareExpirationReminders()` — finds shares whose creator has an email,
  that are fully uploaded (`uploadLocked: true`), expiring within the
  configured threshold, not already reminded, and not set to "never expire"
  (the `moment(0)` sentinel used by `deleteExpiredShares`). Sends one email
  per matching share, best-effort per-share (`try/catch` around each send so
  one bad address or SMTP hiccup doesn't block the rest of the batch and
  doesn't falsely mark that share as reminded — it'll retry on the next
  tick). Gated behind `smtp.enabled` and the new
  `share.enableShareExpirationReminders` toggle, same pattern as the
  existing download-notification gate in `file.service.ts`.
- `backend/src/jobs/jobs.module.ts`: wired in `EmailModule`.
- `backend/src/share/share.service.ts`: `update()` now resets
  `expirationReminderSentAt` back to `null` whenever a share's expiration is
  changed — so a sender who extends their share right after getting
  reminded becomes eligible for a fresh reminder before the new, later
  deadline, instead of never hearing from Send again.
- `backend/src/i18n/en-US/email.json`: added the one new fallback key
  (`shareExpirationReminderNameFallback`) this needed, same "en-US only for
  now, Crowdin picks it up over time" pattern as every other i18n addition
  in this repo.
- `frontend/src/i18n/translations/en-US.ts`: admin-config-page labels and
  descriptions for the 4 new settings (`admin.config.share.*`,
  `admin.config.email.*`), following the exact existing
  `admin.config.{category}.{camelToKebab(name)}` key convention — without
  these the new fields in `/admin/config/share` and `/admin/config/email`
  would render with their raw i18n id instead of real copy.
