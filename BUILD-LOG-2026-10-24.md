## Round 2 — Developer API keys (DONE — backend + frontend, verified end-to-end)

Picked backlog item #6 above: **developer API keys**. It's the
prerequisite for item #7 (webhook delivery) and the single biggest gap for
any founder, small team, or developer who wants to script against Send
instead of clicking through the browser — until now there was no way to
authenticate the API at all without a browser session cookie.

### What shipped

- `backend/prisma/schema.prisma`: new `ApiKey` model (`name`, `keyId`
  (unique, plaintext), `secretHash` (argon2), `lastUsedAt`, `expiresAt`,
  owning `userId`) + `User.apiKeys` relation. Migration
  `20261023214738_add_api_keys` created and applied against a temp SQLite
  DB — ready for `prisma migrate deploy` on next real deploy.
- `backend/prisma/seed/config.seed.ts`: two new admin-configurable
  settings under `security` — `enableApiKeys` (boolean, default `true`,
  acts as a kill switch) and `maxApiKeysPerUser` (number, default `10`).
- `backend/src/apiKey/`: new module.
  - `apiKey.service.ts` — mints tokens as `vcp_<keyId>.<secret>`: `keyId`
    is a random, plaintext, indexed lookup half; `secret` is a separate
    32-byte random half that's argon2-hashed and never stored in
    recoverable form. `authenticate(token)` looks up by `keyId` (one
    indexed query, not a table scan), `argon2.verify`s the secret,
    rejects expired keys/deactivated users, and best-effort bumps
    `lastUsedAt` without blocking the request. `create()` enforces
    `maxApiKeysPerUser` and the `enableApiKeys` kill switch. `revoke()` is
    scoped to `(id, userId)` so one user can never delete another's key.
  - `apiKey.controller.ts` — `GET/POST /apiKeys`, `DELETE /apiKeys/:id`,
    guarded by `SessionOnlyGuard` (new, cookie-only, no fallbacks at all)
    — deliberately **not** reachable with an API key, so a leaked key can
    never mint itself more keys.
  - `apiKey.module.ts` — `@Global()`, same reasoning as
    `PrismaModule`/`ConfigModule`: `ApiKeyService` backs auth guards used
    by controllers in `share`/`file`, which would otherwise all need to
    explicitly import this module.
- `backend/src/auth/guard/jwtOrApiKey.guard.ts` (new) — sibling of
  `JwtGuard`, not a change to it: tries a `vcp_...` key from
  `Authorization: Bearer`/`x-api-key` first, then falls back to the
  existing cookie-JWT + `allowUnauthenticatedShares` behavior, unchanged.
  `CreateShareGuard`, `ShareOwnerGuard`, `ShareSecurityGuard` (and, by
  inheritance, `RegisteredShareOwnerGuard`, `StrictShareOwnerGuard`,
  `FileSecurityGuard`) now extend this instead of `JwtGuard`, so API keys
  work for creating/listing/updating/completing/deleting a share and
  uploading/downloading/deleting its files — the real "developer API"
  surface — while account management, admin config, and password/TOTP
  endpoints keep using plain `JwtGuard`/session auth untouched. A leaked
  API key's blast radius is therefore scoped to shares/files, never
  account takeover or admin access.
- `backend/src/share/share.controller.ts`: the plain `GET /shares` ("my
  shares") route now also accepts `JwtOrApiKeyGuard`.
- `backend/src/i18n/en-US/apiKey.json` (new): `notFound`, `disabled`,
  `maxApiKeysExceeded` error strings, same pattern as every other feature.
- Frontend: `/account/apiKeys` page (list, create-with-expiry modal,
  show-once-copy-the-token modal, revoke with confirm), reachable from
  both the desktop avatar menu and the mobile profile menu
  (`navbar.avatar.api-keys`). `apiKey.service.ts` client,
  `apiKey.type.ts`, and the full `account.apiKeys.*` / two new
  `admin.config.security.*` i18n blocks in `en-US.ts`.

### Verified end-to-end for real

Booted the actual Nest `AppModule` as a real listening HTTP server (not
just `createApplicationContext`) against a scratch SQLite DB seeded with
the real `config.seed.ts`, created a real user, then drove it entirely
over `fetch()` against `http://127.0.0.1:56789/api`:

- Minted a key via `ApiKeyService.create()`, confirmed the token shape and
  that `list()` never leaks `secretHash`.
- `POST /shares` with `Authorization: Bearer <key>` → **201**, confirmed
  the persisted row's `creatorId` really is the key's owner.
- `POST /shares/:id/complete` with the same key → **202**.
- `GET /shares` with `x-api-key: <key>` → **200**, the completed share
  shows up in the list (so both header styles work, and the full
  create→complete→list developer flow works with zero cookies involved).
- `DELETE /shares/:id` with the key → **200**.
- A garbage key, a key with the right `keyId` but a tampered secret, a
  revoked key, an expired key, and a valid key while
  `security.enableApiKeys` is toggled off via the real `ConfigService.update()`
  → all **403** (`CanActivate` returning `false` through Nest's default,
  same as the pre-existing `JwtGuard` fallback path — not 401, which only
  fires when passport itself throws, confirmed by contrast in the next
  check).
- `GET /apiKeys` (key management itself) with only the API key, no
  session cookie → **401** (real passport-thrown `UnauthorizedException`
  from `SessionOnlyGuard`), proving a key cannot be used to mint more
  keys.
- Re-checked `list()` after revoke: the key is gone.
- `npx tsc --noEmit` clean on backend and frontend. `npx nest build` and
  `npx next build` both succeed (`/account/apiKeys` registers as a normal

  pre-existing stub-typing pattern for its other mocks, needed because

  that the existing unit test now has to stub. `npx jest`: 39/39 passing
  unchanged (no new test files added, per the owner's no-new-tests rule —
