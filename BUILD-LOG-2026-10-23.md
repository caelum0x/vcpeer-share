### 1. Config fix — real caps instead of false marketing claims (DONE)

- `deploy/config.yaml`: `share.maxSize` 2 GB → **5 GB**, `share.maxExpiration`
  30 days → **0 (unlimited, "including never")**. Deliberately did **not**
  raise `maxSize` to the box's literal free-disk ceiling as the backlog
  item suggested — `ssh box "df -h /"` showed only **7.9 GB free, 92%
  used**, shared with every other live product on `130.61.180.42`. Setting
  the cap that high would let one upload take down unrelated products.
  5 GB is a real, meaningful raise (bigger than WeTransfer's 3 GB and
  Smash's 2 GB free tiers) that leaves headroom.
- `frontend/src/pages/wetransfer-alternative/index.tsx` (copy only, via
  `en-US.ts`): the "None enforced by the app" claim was also false at any
  cap, so it's now "Up to 5 GB per transfer" — matches reality instead of
  requiring reality to match an unbounded claim.
- `backend/src/constants.ts`: added `MARKETING_CLAIMED_MAX_SIZE_BYTES` /
  `MARKETING_CLAIMED_MAX_EXPIRATION_DAYS`.
- `backend/src/config/config.service.ts`: new
  `checkMarketingClaimsConsistency()`, called from `initialize()` at boot.
  Logs a `CONFIG DRIFT` warning if the running `share.maxSize` /
  `share.maxExpiration` ever diverge from those constants again. Verified
  live — booting against the (lower, default) seed config correctly
  printed the warning; booting against `deploy/config.yaml`'s values
  would not.
- `frontend/src/utils/marketingLimits.util.ts`: frontend mirror of the
  same numbers for the landing-page copy to reference.

### 4. Per-share analytics (DONE — backend + frontend, verified end-to-end)

- `backend/prisma/schema.prisma`: new `ShareAccessEvent` model (shareId,
  action `"view"|"download"`, sha256 IP hash, country, referrer,
  createdAt), indexed on `shareId` and `(shareId, createdAt)`. Migration
  `20261023152537_add_share_access_event_and_source` created and applied
  against a temp dev DB — ready for `prisma migrate deploy` on next real
  deploy.
- `backend/src/shareAnalytics/` (new module): `ShareAnalyticsService`
  (`recordAccess` — best-effort, never throws, so analytics can never
  break a real file view/download; `getAnalytics` — aggregates total
  views/downloads, unique visitors by ip-hash, top countries, top
  referrers, a daily timeline, and an expiry countdown) and
  `ShareAnalyticsController` exposing `GET /shares/:id/analytics` behind
  the same `ShareOwnerGuard` already used by `PATCH`/`DELETE
  /shares/:id`.
  - Country comes from the `CF-IPCountry` header Cloudflare already sets
    on every request to `share.vcpeer.com` — no third-party GeoIP lookup,
    no new paid service, matching the "spend zero money" constraint.
  - **Deliberately hooked at the controller layer**
    (`ShareController.get`, `FileController.getFile`/`getZip`), not inside
    `ShareSecurityGuard`/`FileSecurityGuard` as the backlog text literally
    suggested — those guards have already been through two TOCTOU race
    fixes this month (`6302d7d0`, `69872842`) and are delicate; recording
    only once a controller actually serves content is equivalent in
    practice (every event is still real, already-authorized traffic) and
    doesn't risk reopening either of those race fixes.
    - Range requests (video/audio scrubbing) are deliberately not
      double-counted — recording only fires on `!file.range` requests, or
      every seek in a video preview would have inflated the view count.
- `backend/src/file/file.module.ts`, `backend/src/share/share.module.ts`,
  `backend/src/app.module.ts`: wired the new module in.
- Frontend: `frontend/src/components/account/ShareAnalyticsChart.tsx` — a
  dependency-free inline-SVG grouped bar chart (views vs. downloads per
  day); no charting library pulled in for this. `frontend/src/pages/
  account/shares/[shareId]/analytics.tsx` — stat tiles (views, downloads,
  unique visitors, expiry countdown), the chart, and top-countries /
  top-referrers tables. Linked from a new chart-icon action on
  `frontend/src/pages/account/shares.tsx`.
- `frontend/src/types/share.type.ts`, `frontend/src/services/share.service.ts`:
  `ShareAnalytics` type and `shareService.getAnalytics(id)`.
- **Verified end-to-end for real**, not just type-checked: booted the
  Nest backend against a scratch SQLite DB, created a share via the real
  HTTP API, uploaded a real file, opened it inline (`view`), downloaded it
  (`download`), hit `/zip`, then called `GET /shares/:id/analytics` and
  got back correct aggregated counts (`totalViews: 1, totalDownloads: 1,
  uniqueVisitors: 1`, country/referrer breakdowns, a populated timeline,
  and a correct `expiresInMs`). Also ran a full `next build` that compiled
  the new page as a route, and spot-checked it rendering without a 500 via
  `next dev`.
